> **重大架構演進說明（2.3 → 17）**：
> 1. **64 位元 / 雙 ABI Zygote 腳本拆分、`init` C++ 重寫與權限收緊**：原書 2.3 把單一 `service zygote /system/bin/app_process` 直接寫死在 `init.rc`，socket 權限為寬鬆的 `666`；Android 17 的 `init.rc` 依 `ro.zygote` 屬性動態 `import /system/etc/init/hw/init.${ro.zygote}.rc`（純 64 位元 `init.zygote64.rc` 或雙 ABI `init.zygote64_32.rc`），透過 `on zygote-start`（等待 `odsign.verification.done`）觸發 `start zygote` / `start zygote_secondary`。socket 改為成對的 `zygote` 與 `usap_pool_primary`（權限收緊為 `660 root system`），加上 `critical` 與 `onrestart` 連動重啟（`audioserver`、`cameraserver`、`media`、`netd`、`wificond` 等）。`init` 本體亦自 C 語言 `init.c` / `util.c` 全面重寫為 C++ `Service::Start()` / `SocketDescriptor::Create()` / `Descriptor::Publish()`，建立 socket 時強制 `SOCK_CLOEXEC` 並附加 SELinux context，待子進程 `RunService()` 發布環境變數時才清掉 `FD_CLOEXEC`。
> 2. **Dalvik → ART、安全預載與 `ZygoteServer`（`Os.poll` + USAP 池 + `Runnable` 跳板）**：`AndroidRuntime::start()` 檢查 APEX 路徑（`ANDROID_ART_ROOT` / `ANDROID_I18N_ROOT` / `ANDROID_TZDATA_ROOT`），經 `JniInvocation::Init` 載入 ART（`libart.so`）建立虛擬機。`ZygoteInit.main()` 以 `ZygoteHooks.startZygoteNoThreadCreation()` 保護單執行緒安全，在 `preloadClasses()` 時暫時降權至 `UNPRIVILEGED_UID/GID (9999)` 執行靜態初始化並 `preloadDexCaches()`，預載擴展至 HAL / 圖形驅動 / WebView / JCA Providers；`Zygote.initNativeState()` 初始化控制 socket、SELinux `seapp_context` 與儲存卸載。Socket 監聽從 `ZygoteInit` 拆出至 `ZygoteServer`，以 `Os.poll(StructPollfd[])` 統一輪詢 `mZygoteSocket`、連線 peers 與可選的 **USAP（Unspecialized App Process）預孵化池**（原書 2.3 的 `runForkMode` 已移除）。最關鍵的流程控制翻轉：子進程入口不再**拋出 `ZygoteInit.MethodAndArgsCaller` 例外**，而是由 `forkSystemServer()` / `runSelectLoop()` **返回 `Runnable`（`RuntimeInit.MethodAndArgsCaller`）**回到 `ZygoteInit.main()` 執行 `r.run()`，同樣清乾淨呼叫堆疊卻零例外開銷。
> 3. **`system_server` 徹底重構：`init1/init2` 與 `ServerThread` 消亡、`SystemServiceManager` 四階段 + Boot Phases + APEX 服務**：原書 2.3 中 `SystemServer.main()` 呼叫原生 `init1()` → `system_init()` 註冊 `GrimReaper` 監控 `servicemanager`、在同進程啟動 `SurfaceFlinger` / `SensorService`，再回呼 `init2()` 另開 `ServerThread` 手工 `new` 各服務並直接 `ServiceManager.addService`。Android 17 中：`SurfaceFlinger` 已獨立為 `init` 服務進程，`system_init.cpp` / `init1()` / `init2()` / `ServerThread` 全數移除；`SystemServer.main()` 直接在主執行緒跑 `new SystemServer().run()`——載入 `libandroid_servers.so`（提供 `startIStatsService` / `startMemtrackProxyService` / `startISensorManagerService` / `startIncrementalService` 等少量 JNI 服務），呼叫 `Looper.prepareMainLooper()`、`SystemServerInitThreadPool.start()`、`createSystemContext()`（`ActivityThread.systemMain()`），並由 **`SystemServiceManager`** 統一管理四大啟動階段（`startBootstrapServices` → `startCoreServices` → `startOtherServices` → `startApexServices` + `sealStartedServices()`）與細粒度 **`SystemService.PHASE_*` 啟動階段回呼**（100 → 200 → 480 → 500 → 520 → 550 → 600 → 1000），最後進入 `Looper.loop()`；而 `system_server` 崩潰則由 Zygote 原生 `SigChldHandler` 偵測 `pid == gSystemServerPid` 後自殺（`SIGKILL`），觸發 `init` 整套重啟。

## 三、各節情景與呼叫鏈（起點 → 終點）

### 11.1 Zygote 進程的啟動腳本與 `init` 服務孵化機制（`11.1-zygote-init-script.md`）
- **情景**：系統開機完成檔案系統掛載與 `odsign` 驗證後，`init` 進程依 `ro.zygote` 屬性載入 Zygote 服務腳本，建立 `/dev/socket/zygote` 與 `/dev/socket/usap_pool_primary`，透過環境變數將 socket fd 繼承給新孵化的 `/system/bin/app_process64` 進程。
- **起點 → 終點**：
  - 腳本載入與觸發：`system/core/rootdir/init.rc`（`import /system/etc/init/hw/init.${ro.zygote}.rc`、`trigger zygote-start` → `on zygote-start`：`wait_for_prop odsign.verification.done 1` → `start zygote` / `start zygote_secondary`）→ `init.zygote64.rc` / `init.zygote64_32.rc`（`service zygote /system/bin/app_process64 -Xzygote /system/bin --zygote --start-system-server --socket-name=zygote`、`socket zygote stream 660 root system`、`socket usap_pool_primary stream 660 root system`、`onrestart`、`critical`）
  - 服務啟動與 Socket 建立：`init/service.cpp::Service::Start()`（驗證執行檔、計算 SELinux context、遍歷 `sockets_` 呼叫 `SocketDescriptor::Create()`）→ `init/service_utils.cpp::SocketDescriptor::Create()` → `init/util.cpp::CreateSocket()`（`setsockcreatecon`、`socket(PF_UNIX, type | SOCK_CLOEXEC, 0)`、綁定 `/dev/socket/<name>`、`lchown`/`fchmodat`、`listen()`，封裝為 `Descriptor("ANDROID_SOCKET_" + name, fd)`）
  - 孵化與發布至子進程：`Service::Start()` 呼叫 `fork()` → 子進程進入 `Service::RunService()` → 呼叫 `Descriptor::Publish()`（`fcntl` 移除 `FD_CLOEXEC`、`setenv("ANDROID_SOCKET_zygote", "<fd>", 1)`）→ 等待父進程 cgroups 就緒 → `SetTaskProfiles` / `SetProcessProfiles` → `SetProcessAttributesAndCaps()` → `ExpandArgsAndExecv()`（`execv("/system/bin/app_process64", ...)`）。

### 11.2 Zygote 進程的啟動過程（`11.2-zygote-startup.md`）
- **情景**：`init` 執行 `execv("/system/bin/app_process64", ...)` 後，Zygote 進程從 C++ `main()` 啟動 ART 虛擬機、註冊框架 JNI、預載共用類與資源、接管 `init` 建立的雙 Control Socket、孵化 `system_server` 子進程，最後進入 `Os.poll()` 輪詢循環等待 AMS（`ZygoteProcess`）的連線請求。
- **起點 → 終點**：
  - Native 入口與參數整理：`app_main.cpp::main()`（建 `AppRuntime`、`computeArgBlockSize` 保留改名空間、分離 VM 選項 `-Xzygote` 與 `--zygote` / `--start-system-server` / `--socket-name=zygote`、`maybeCreateDalvikCache()`、讀取 `ro.product.cpu.abilist64` 組成 `--abi-list=...`、`runtime.setArgv0("zygote64", true)`）→ `runtime.start("com.android.internal.os.ZygoteInit", args, true)`
  - ART VM 建立與 JNI 註冊：`AndroidRuntime::start()`（記錄 `LOG_BOOT_PROGRESS_START`、檢查 `ANDROID_ROOT` / `ANDROID_ART_ROOT` / `ANDROID_I18N_ROOT` / `ANDROID_TZDATA_ROOT`、`JniInvocation::Init(NULL)`、`startVm()` 呼叫 `JNI_CreateJavaVM`、`onVmCreated(env)`、`startReg(env)` 註冊全體 `gRegJNI`、`CallStaticVoidMethod(ZygoteInit.main, strArray)`）
  - Java 層預載與原生狀態初始化：`ZygoteInit.main()`（`ZygoteHooks.startZygoteNoThreadCreation()`、`Os.setpgid(0, 0)`、`RuntimeInit.preForkInit()`、解析 `start-system-server` / `--enable-lazy-preload` / `--abi-list=` / `--socket-name=` → `preload()`〔`beginPreload` → `preloadClasses()` 暫降 UID/GID=9999 載入 `/system/etc/preloaded-classes` + `preloadDexCaches()` → `cacheNonBootClasspathClassLoaders()` → `Resources.preloadResources()` → `nativePreloadAppProcessHALs()` / `maybePreloadGraphicsDriver()` → `preloadSharedLibraries()` → `WebViewFactory.prepareWebViewInZygote()` → `endPreload()` → `warmUpJcaProviders()`〕→ `gcAndFinalize()` → `Zygote.initNativeState(isPrimaryZygote)`〔`android_get_control_socket`、`initUnsolSocketToSystemServer`、`selinux_android_seapp_context_init`、`UnmountStorageOnInit`、`SetTaskProfiles`〕→ `ZygoteHooks.stopZygoteNoThreadCreation()`）
  - Server Socket 建置與孵化 `system_server`：`new ZygoteServer(isPrimaryZygote)`（`Zygote.getUsapPoolEventFD()`、`Zygote.createManagedSocketFromInitSocket("zygote")` / `"usap_pool_primary"` 讀取 `ANDROID_SOCKET_*` 建 `LocalServerSocket`、`fetchUsapPoolPolicyProps()`）→ `ZygoteInit.forkSystemServer()`（計算 capabilities 交集、組裝硬編碼參數、`ZygoteArguments.getInstance`、設定 MTE/TBI/GWP-ASan 旗標、`Zygote.forkSystemServer()` → `ZygoteHooks.preFork()` → `nativeForkSystemServer` → `zygote::ForkCommon()`〔`SetSignalHandlers()` 裝 `SigChldHandler`、封鎖 `SIGCHLD`、關 log/stats fd、`FileDescriptorTable` 檢查、`mallopt(M_PURGE_ALL)`、`fork()`〕→ 父進程記錄 `gSystemServerPid` 並 `waitpid(WNOHANG)` 檢活，返回 `null`）
  - 主輪詢循環：`ZygoteServer.runSelectLoop(abiList)`（組合 `StructPollfd[]`〔`mZygoteSocket` + 已連線 peers + 若啟用 USAP 則加上 `mUsapPoolEventFD` 與 `usapPipeFDs`〕→ `Os.poll(pollFDs, pollTimeoutMs)` → `pollIndex == 0` 時 `acceptCommandPeer()` 建立 `ZygoteConnection`；已連線 peer 就緒時呼 `connection.processCommand(this, multipleForksOK)`；USAP FD 就緒時回收表項並依策略 `fillUsapPool()`）。

### 11.3 System 進程（`system_server`）的啟動過程（`11.3-system-server-startup.md`）
- **情景**：`ZygoteInit.forkSystemServer()` 透過 `fork()` 產出 `system_server` 子進程後，子進程完成原生層權限特化、建立系統專屬 `ClassLoader`、開啟 Binder 執行緒池，經 `Runnable` 跳板進入 `SystemServer.main()`，依序啟動 Bootstrap / Core / Other / APEX 四階段系統服務並進入主執行緒 `Looper.loop()`。
- **起點 → 終點**：
  - 子進程原生特化與準備：`com_android_internal_os_Zygote_nativeForkSystemServer`（`pid == 0`）→ `SpecializeCommon()`（設定 `uid=1000` / `gid=1000` / `setgroups`、`capset`、SELinux 轉域、`callPostForkSystemServerHooks` 觸發 `ZygoteHooks.postForkSystemServer`、於 Zygote SELinux 域下預建 `getOrCreateSystemServerClassLoader` 與 `prefetchStandaloneSystemServerJars`）→ 返回 `ZygoteInit.forkSystemServer`（`hasSecondZygote` 時 `waitForSecondaryZygote`、`zygoteServer.closeServerSocket()`）→ `ZygoteInit.handleSystemServerProcess(parsedArgs)`（`Os.umask(0077)`、`Process.setArgV0("system_server")`、`getOrCreateSystemServerClassLoader()` 設為 `ContextClassLoader`）
  - 啟動 Binder 執行緒池與反射跳板：`ZygoteInit.zygoteInit(...)` → `RuntimeInit.redirectLogStreams()` → `RuntimeInit.commonInit()` → `ZygoteInit.nativeZygoteInit()` → `AndroidRuntime.cpp::com_android_internal_os_ZygoteInit_nativeZygoteInit` → `AppRuntime::onZygoteInit()`（`ProcessState::self()->startThreadPool()`）→ `RuntimeInit.applicationInit()`（`nativeSetExitWithoutCleanup(true)`、設 `targetSdkVersion`）→ `RuntimeInit.findStaticMain("com.android.server.SystemServer", ...)` 返回 `new RuntimeInit.MethodAndArgsCaller(m, argv)` → 一路返回 `ZygoteInit.main()` 執行 `r.run()` 呼叫 `SystemServer.main()`
  - `SystemServer.run()` 主執行緒前置準備：`new SystemServer().run()`（設定 `Binder.setWarnOnBlocking(true)`、`VMRuntime.clearGrowthLimit()`、`BinderInternal.setMaxThreads(31)`、`Looper.prepareMainLooper()`、`SystemServerInitThreadPool.start()`、`System.loadLibrary("android_servers")`、`ApplicationSharedMemory.create()`、`createSystemContext()`〔`ActivityThread.systemMain()`〕、建立 `SystemServiceManager` 並註冊至 `LocalServices`）
  - 四階段系統服務與 Boot Phases 推進：
    1. `startBootstrapServices()`：`Watchdog`、`Installer`、`startIStatsService()` / `startMemtrackProxyService()`、`ATMS`、`AMS`、`PowerManagerService`、`DisplayManagerService` → `PHASE_WAIT_FOR_DEFAULT_DISPLAY (100)` → `PackageManagerService.main()` → `UserManagerService` → `mActivityManagerService.setSystemProcess()`
    2. `startCoreServices()`：`SystemConfigService`、`BatteryService`、`UsageStatsService`、`WebViewUpdateService` 等
    3. `startOtherServices()`：`ContentService.Lifecycle`、`PHASE_WAIT_FOR_SENSOR_SERVICE (200)`、`WindowManagerService.main()`、`startISensorManagerService()` → `PHASE_LOCK_SETTINGS_READY (480)` → `PHASE_SYSTEM_SERVICES_READY (500)` → `PHASE_DEVICE_SPECIFIC_SERVICES_READY (520)` → `mActivityManagerService.systemReady(...)` 回呼推進 `PHASE_ACTIVITY_MANAGER_READY (550)` 與 `PHASE_THIRD_PARTY_APPS_CAN_START (600)`
    4. `startApexServices()`：從 `ApexManager.getApexSystemServices()` 載入 Mainline APEX 服務並 `mSystemServiceManager.sealStartedServices()`
  - 主迴圈永駐：`Looper.loop()`（並對照 Zygote `SigChldHandler` 偵測 `pid == gSystemServerPid` 後自殺觸發 `init` 重啟的容錯閉環）。

> **重大架構演進說明（2.3 → 17）**：
> 1. **獨立服務化與 7 階段 `InputListener` 管線（含 Rust `IInputFlingerRust`）**：原書 2.3 的 `InputManager` 是 `WindowManagerService` 內部私有物件，且 `InputReader` 直接呼叫 `InputDispatcher`。Android 17 中，Java 層抽離為獨立系統服務 `InputManagerService`（`SystemServer` 透過 `InputManagerService.Lifecycle` 啟動，再透過 `NativeInputManagerService$NativeImpl` 橋接 JNI `NativeInputManager`），C++ `InputManager` 同時繼承 `BnInputFlinger` 註冊為 `"inputflinger"` 系統服務，並經由 `cxxbridge` 啟動 Rust 元件 `IInputFlingerRust`；事件流改為可擴充的 7 階段 `InputListener` 管線（每階段包一層 `TracedInputListener`）：**`InputReader` → `UnwantedInteractionBlocker` → `PointerChoreographer` → `InputProcessor` → `InputDeviceMetricsCollector` → `InputFilter`（Rust 後端）→ `InteractionReporter`（可選）→ `InputDispatcher`**。
> 2. **`InputChannel` 底層傳輸由「Ashmem + 雙向雙 Pipe」全面改為「單一 `SOCK_SEQPACKET` SocketPair + `BBinder` Token」**：原書 2.3 用 8 KiB Ashmem 共享記憶體存資料，搭配兩條單向管道（`mReceivePipeFd` / `mSendPipeFd`）傳遞 1 位元組訊號。Android 17 徹底廢除 Ashmem 與雙管道，改為單一雙向 Unix Domain **`socketpair(AF_UNIX, SOCK_SEQPACKET, 0, sockets)`**（收發緩衝區各 32 KiB），直接收發具訊息邊界的 `InputMessage` 結構體（含 `KEY`、`MOTION`、`FINISHED`、`FOCUS`、`CAPTURE`、`DRAG`、`TIMELINE`、`TOUCH_MODE`），發送前以 `getSanitizedCopy()` 清零結構填充位元組防資訊洩漏，並為 `KEY`/`MOTION` 加上 HMAC-SHA256 驗證簽章；每對 `InputChannel` 共享一枚 `BBinder` `token` 作為連線識別。建立與 Server 註冊也合併為單一原子步驟 `InputDispatcher::createInputChannel()`，僅將 Client 端經 `InputChannelCore` Parcel 傳回應用進程。
> 3. **視窗清單與輸入焦點改由 `SurfaceFlinger` 統一同步（`WindowInfosListener` + `FocusResolver`）**：原書 2.3 由 WMS `InputMonitor.updateInputWindowsLw()` 直接經 JNI 呼叫 `InputManager.setInputWindows()` 推送視窗與焦點。Android 17 中，為確保「畫面上看得到的 Z-order / 遮擋／變換矩陣」與「輸入命中與焦點」嚴格一致，WMS `InputMonitor` 改透過 `SurfaceControl.Transaction.setInputWindowInfo()` 與 `setFocusedWindow()` 隨圖層事務送往 **`SurfaceFlinger`**；再由 `SurfaceFlinger` 的 `BackgroundExecutor` 分別透過 `mWindowInfosListenerInvoker` 回呼 `InputDispatcher::DispatcherWindowListener::onWindowInfosChanged()`，以及透過 Binder 呼叫 `IInputFlinger::setFocusedWindow()` 交由多螢幕 **`FocusResolver`** 裁決焦點並發送 `InputMessage::Type::FOCUS`。
> 4. **應用端由 `InputQueue` / `InputHandler` 演進為 `InputEventReceiver` + 7 階段 `InputStage` 管線，且註銷順序嚴格反轉**：原書 2.3 使用全域 `InputQueue` + `NativeInputQueue` 與 `ViewRoot.mInputHandler` 直接派發按鍵；Android 17 改由每個視窗獨享 `ViewRootImpl.WindowInputEventReceiver`（繼承 `InputEventReceiver`，JNI 為繼承 `LooperCallback` 與 `MessageHandler` 的 `NativeInputEventReceiver`，內含無鎖 `BlockingQueue<OutboundEvent>` 支援 `Finish` 與 `Timeline` 回報），並將事件送入 7 階段 **`InputStage`** 責任鏈（`NativePreIme` → `ViewPreIme` → `Ime` → `EarlyPostIme` → `NativePostIme` → `ViewPostIme` → `Synthetic`）才進入 `DecorView` / `Activity`。而在銷毀視窗時（`ViewRootImpl.dispatchDetachedFromWindow()`），Android 17 **反轉了原書的註銷順序**：**先**呼叫 `mWindowSession.remove()` 註銷 Server 端 `InputChannel`，**後**呼叫 `mInputEventReceiver.dispose()` 關閉 Client 端 socket，明確避免提前關閉 Client 端觸發 Server 端 `ALOOPER_EVENT_HANGUP` 斷線誤報。

## 三、各節情景與呼叫鏈（起點 → 終點）

### 14.1 鍵盤消息處理模型（`14.1-input-model.md`）
- **情景**：剖析 Android 17 中實體按鍵（或系統鍵盤事件）如何跨越 Linux 核心 `evdev`、`system_server`（`InputManagerService` / `inputflinger` / WMS）、`surfaceflinger` 與應用進程主執行緒 `Looper`（承接第 13 章），形成端到端、可驗證且防 ANR 的事件分發與完成回執閉環。
- **核心脈絡**：核心資料結構與三進程協作拓撲總覽（`InputManager` 7 階段 `InputListener` 管線、`EventHub`、`InputReader`、`InputDispatcher` / `FocusResolver` / `ConnectionManager`、`InputChannel` `SOCK_SEQPACKET` + `InputMessage`、`NativeInputEventReceiver` + `InputStage`），為後續 14.2–14.5 節建立全景地圖。

### 14.2 `InputManagerService` 的啟動過程（`14.2-input-manager-startup.md`）
- **情景**：系統開機階段（承接 11.3 節 `SystemServer.startOtherServices()`），`system_server` 啟動獨立的 `InputManagerService` 與 `WindowManagerService`，初始化 C++ `InputManager` 7 階段管線與 Rust `IInputFlingerRust`，並拉起 `InputDispatcher` 與 `InputReader` 兩條即時輸入執行緒開始監聽 `/dev/input` 裝置節點。
- **起點 → 終點**：
  - 建立服務與管線：`SystemServer.startOtherServices()` → `mSystemServiceManager.startService(InputManagerService.Lifecycle.class)` → `new InputManagerService(context)` → `new NativeInputManagerService.NativeImpl(service, looper.getQueue(), context)` → `com_android_server_input_InputManagerService.cpp::nativeInit()` → `new NativeInputManager()` → `new InputManager(...)`（`createInputFlingerRust()` + 由尾到頭串接 `InputDispatcher` … `InputReader` 7 階段 `TracedInputListener`）+ `defaultServiceManager()->addService("inputflinger", im)`
  - 啟動服務與執行緒：`SystemServer` 綁定 `inputManager.setWindowManagerCallbacks(wm.getInputManagerCallback())` → `InputManagerService.start()` → `nativeStart()` → `InputManager::start()`
  - 啟動 `InputDispatcher`：`InputDispatcher::InputDispatcher()`（透過 `SurfaceComposerClient::getDefault()->addWindowInfosListener(mWindowInfoListener)` 訂閱視窗資訊）→ `InputDispatcher::start()` → `new InputThread("InputDispatcher", dispatchOnce, wake)` → `dispatchOnce()` → `mLooper->pollOnce(timeoutMillis)` 進入 `epoll_wait` 休眠
  - 啟動 `InputReader` 與 `EventHub`：`InputReader::start()` → `new InputThread("InputReader", loopOnce, wake)` → `InputReader::loopOnce()` → `EventHub::EventHub()`（`epoll_create1(EPOLL_CLOEXEC)`、`inotify_init1(IN_CLOEXEC)` 監看 `/dev/input`、`pipe2(wakeFds, O_CLOEXEC)`）→ `EventHub::getEvents()` → `handleDeviceChangesLocked()` → `scanDevicesLocked()` → `scanDirLocked("/dev/input")` → `openDeviceLocked()`（讀取 `EVIOCGNAME` / `EVIOCGBIT`、分類裝置與註冊 `EPOLLIN | EPOLLWAKEUP`）。

### 14.3 `InputChannel` 的建立、註冊與焦點窗口同步（`14.3-register-input-channel.md`）
- **情景**：Activity 啟動完成首次顯示視窗時，呼叫 `ViewRootImpl.setView()` 向 `WindowManagerService` 添加視窗；系統為該視窗建立成對 `InputChannel` 並完成 Server 端註冊，再經由 `SurfaceFlinger` 將視窗拓撲與焦點狀態同步給 `InputDispatcher`，最後由應用進程將 Client 端 `InputChannel` 掛載到主執行緒 `Looper` 並組裝 `InputStage` 管線。
- **起點 → 終點**：
  - 建立與 Server 端註冊：`ViewRootImpl.setView()`（建立空 `InputChannel` 占位）→ `mWindowSession.addToDisplayAsUser(..., inputChannel)` → `Session.addToDisplayAsUser()` → `WindowManagerService.addWindow()` → `WindowState.openInputChannel()` → `InputManagerService.createInputChannel(name)` → `NativeInputManager::createInputChannel()` → `InputDispatcher::createInputChannel()`（呼叫 `InputChannel::openInputChannelPair()` 建立 `socketpair(AF_UNIX, SOCK_SEQPACKET)` + 32 KiB 緩衝區 + 共用 `BBinder token`；以 `mConnectionManager.createConnection()` 將 Server 端註冊進 `InputDispatcher` 的 `mLooper` 綁定 `handleReceiveCallback`；回傳 Client 端 `InputChannel`）→ `channel.copyTo(outInputChannel)` 經 Binder `InputChannelCore` 傳回應用進程
  - 焦點窗口與視窗拓撲同步：WMS 更新焦點 `InputMonitor.setInputFocusLw()` → `updateInputWindowsLw()` → `UpdateInputForAllWindowsConsumer.updateInputWindows()`（呼叫 `populateInputWindowHandle()` + `SurfaceControl.Transaction.setInputWindowInfo()` 及 `requestFocus()` → `mInputTransaction.setFocusedWindow(mInputFocus, windowName, mDisplayId)`）→ `SurfaceFlinger` 事務提交後於 `BackgroundExecutor` 執行 `mWindowInfosListenerInvoker->windowInfosChanged()`（回呼 `InputDispatcher::DispatcherWindowListener::onWindowInfosChanged()` → `setInputWindowsLocked()`）與 `inputFlinger->setFocusedWindow(focusRequest)`（呼叫 `InputManager::setFocusedWindow()` → `InputDispatcher::setFocusedWindow()` → `mFocusResolver.setFocusedWindow()` → `onFocusChangedLocked()`）
  - Client 端註冊與管線組裝：`ViewRootImpl.setView()` 建立 `new WindowInputEventReceiver(inputChannel, Looper.myLooper(), ...)` → `InputEventReceiver` 建構子呼叫 `nativeInit()` → `android_view_InputEventReceiver.cpp` 建立 `NativeInputEventReceiver`（持有 `InputConsumer`）→ `initialize()` → `setFdEvents(ALOOPER_EVENT_INPUT)` → `mMessageQueue->getLooper()->addFd(fd, 0, ALOOPER_EVENT_INPUT, this, nullptr)`；接著組裝 7 階段 `InputStage` 管線（`mFirstInputStage = nativePreImeStage`、`mFirstPostImeInputStage = earlyPostImeStage`）。

### 14.4 鍵盤消息的分發過程（`14.4-dispatch-key-event.md`）
- **情景**：使用者按下實體鍵盤上的按鍵，核心 `evdev` 驅動寫入 `struct input_event` 並喚醒阻塞中的 `EventHub`；按鍵事件歷經 `InputReader` 轉換、7 階段 `InputListener` 管線、`InputDispatcher` 焦點目標查找與 HMAC 簽章，透過 `SOCK_SEQPACKET` 送抵焦點應用主執行緒，走完 `InputStage` 與 `DecorView` / `Activity` 視圖分派後回傳 `FINISHED` 確認訊息給 `InputDispatcher` 完成整個分發週期。
- **起點 → 終點**：
  - `InputReader` 取得並轉換按鍵事件：`EventHub::getEvents()`（`epoll_wait` 返回 → `read(device->fd, ...)` 轉為 `RawEvent`）→ `InputReader::loopOnce()` → `processEventsLocked()` → `processEventsForDeviceLocked()` → `InputDevice::process()` → `KeyboardInputMapper::process()` → `processKey()`（查表映射 `scanCode` → `keyCode`、維護 `mKeyDowns` 與 `mMetaState`、產出 `NotifyKeyArgs`）→ 釋鎖後經 `mNextListener.notify(args)` 穿透 7 階段管線抵達 `InputDispatcher::notifyKey()`（`mPolicy.interceptKeyBeforeQueueing()` → 入隊 `mInboundQueue` → `mLooper->wake()`）
  - `InputDispatcher` 派發鍵盤事件：`InputDispatcher::dispatchOnce()` → `dispatchOnceInnerLocked()`（自 `mInboundQueue` 取出 `KeyEntry`）→ `dispatchKeyLocked()`（按鍵長按重複狀態處理、`doInterceptKeyBeforeDispatchingCommand()` 政策攔截 → `findFocusedWindowTargetLocked()` 經 `mFocusResolver` 取得焦點視窗）→ `dispatchEventToCurrentInputTargetsLocked()` → `prepareDispatchCycleLocked()` → `enqueueDispatchEntriesLocked()` → `startDispatchCycleLocked()`（加入 `waitQueue` 與 `mAnrTracker`、`getSignature()` 計算 HMAC → `InputPublisher::publishKeyEvent()` → `InputChannel::sendMessage()` 經 `getSanitizedCopy()` 清零填充後 `::send()` 寫入 socket）
  - 應用進程接收、分派與回覆完成：主執行緒 `Looper::pollInner()` 偵測 socket `EPOLLIN` → `NativeInputEventReceiver::handleEvent()` → `consumeEvents()` → `InputConsumer::consume()`（`mChannel->receiveMessage()` 讀取 `InputMessage::Type::KEY` 並初始化 `KeyEvent`）→ JNI 回呼 `InputEventReceiver.dispatchInputEvent()` → `ViewRootImpl.WindowInputEventReceiver.onInputEvent()` → `enqueueInputEvent()` → `doProcessInputEvents()` → `deliverInputEvent()` → 沿 `InputStage` 責任鏈（`NativePreIme` → `ViewPreIme` → `Ime` → `EarlyPostIme` → `NativePostIme` → `ViewPostImeInputStage.processKeyEvent()` → `mView.dispatchKeyEvent(event)`）→ `DecorView.dispatchKeyEvent()` → `Activity.dispatchKeyEvent()` → `PhoneWindow.superDispatchKeyEvent()` → `KeyEvent.dispatch()` → 結束後 `InputStage.finish()` → `ViewRootImpl.finishInputEvent()` → `InputEventReceiver.finishInputEvent()` → `nativeFinishInputEvent()` → `NativeInputEventReceiver::finishInputEvent()`（寫入 `mOutboundQueue` → `processOutboundEvents()` → `InputConsumer::sendFinishedSignal()` 經 `InputChannel::sendMessage()` 送出 `InputMessage::Type::FINISHED`）
  - `InputDispatcher` 收到完成回執：`InputDispatcher` 的 `mLooper` 偵測 Server 端 socket `EPOLLIN` → `handleReceiveCallback()` → `InputPublisher::receiveConsumerResponse()`（解析 `Finished` / `Timeline`）→ `finishDispatchCycleLocked()` → 排入並執行 `doDispatchCycleFinishedCommand()`（自 `waitQueue` 移除、更新 `mAnrTracker` 與 `mLatencyTracker`、若 `handled == false` 觸發 fallback 處理）→ 呼叫 `startDispatchCycleLocked()` 續派下一筆 `outboundQueue` 事件。

### 14.5 `InputChannel` 的註銷與視窗銷毀過程（`14.5-unregister-input-channel.md`）
- **情景**：前景 Activity 結束並銷毀其視窗時，ATMS 透過 `DestroyActivityItem` 通知應用進程移除 `DecorView` 與 `ViewRootImpl`，並嚴格按照「**先註銷 Server 端、後關閉 Client 端**」的安全順序拆除 `InputChannel` 雙端資源。
- **起點 → 終點**：
  - 銷毀應用程式視窗：`ActivityRecord.destroyImmediately()`（排入 `DestroyActivityItem` 經 `ClientLifecycleManager` 派發）→ `ActivityThread.handleDestroyActivity()` → `WindowManagerImpl.removeViewImmediate(v)` → `WindowManagerGlobal.removeView(view, true)` → `ViewRootImpl.die(true)` → `ViewRootImpl.doDie()` → `ViewRootImpl.dispatchDetachedFromWindow()`（通知 `mFirstInputStage.onDetachedFromWindow()`、`mView.dispatchDetachedFromWindow()`、銷毀硬體渲染與 Surface）
  - **先**註銷 Server 端 `InputChannel`：`ViewRootImpl.dispatchDetachedFromWindow()` 呼叫 `mWindowSession.remove(mWindow.asBinder())` → `Session.remove()` → `WindowManagerService.removeClientToken()` → `WindowState.removeIfPossible()` → `WindowState.removeImmediately()` → `WindowState.disposeInputChannel()` → `InputManagerService.removeInputChannel(mInputChannelToken)` → `NativeInputManager::removeInputChannel()` → `InputDispatcher::removeInputChannel()` → `removeInputChannelLocked()`（`abortBrokenDispatchCycleLocked()` 排空 `outboundQueue`/`waitQueue`、`mAnrTracker.eraseToken()`、`mConnectionManager.removeConnection()` 自 `mLooper` 移除 Server fd 並關閉 socket）
  - **後**註銷 Client 端 `InputChannel`：`ViewRootImpl.dispatchDetachedFromWindow()` 呼叫 `mInputEventReceiver.dispose()` → `InputEventReceiver.dispose(false)` → `nativeDispose(mReceiverPtr)` → `NativeInputEventReceiver::dispose()`（先呼叫 `processOutboundEvents()` 盡力沖刷未送出的 finish 回執以避免 ANR，再呼叫 `setFdEvents(0)` 自應用主執行緒 `Looper` 移除 Client fd、`mInputConsumer.reset()` 釋放 `InputConsumer`、`mMessageQueue->getLooper()->removeMessages(this)`），最後呼叫 `mInputChannel.dispose()` 關閉 Client 端 fd。

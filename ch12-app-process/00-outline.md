> **重大架構演進說明（2.3 → 17）**：
> 1. **`AMS` → `ProcessList` 拆離與無鎖非同步孵化（`ProcStartHandler` + `startSeq`）**：原書 2.3 在 `ActivityManagerService.startProcessLocked()` 內持全域鎖直接同步呼叫 `Process.start()`。Android 17 將進程啟動主邏輯拆入 `ProcessList`，為每次啟動分配單調遞增序號 `startSeq` 並登記於 `mPendingStarts`；在預設開啟 `FLAG_PROCESS_START_ASYNC` 時，透過獨立執行緒的 `mService.mProcStartHandler` **不持有 AMS 全域鎖**執行 `handleProcessStart()`（若存在尚未退出的前任進程 `predecessor.getDyingPid() > 0`，先掛載 `mSuccessorStartRunnable` 等其死亡）→ `startProcess()`（處理 App 資料目錄隔離 `pkgDataInfoMap` / `bindMountAppsData`、DeliQueue 旗標 `useDeliQueue`，並分流一般 Zygote / `WebViewZygote` / `AppZygote`）→ `Process.start()`；取得 `ProcessStartResult(pid, usingWrapper)` 後再加鎖呼叫 `handleProcessStartedLocked()` 寫入 `mPidsSelfLocked` 與排程 `PROC_START_TIMEOUT_MSG`。同時把 `seq=<startSeq>` 傳給新進程，解決子進程搶先呼叫 `attachApplication()` 的非同步競態。
> 2. **`Process` → `ZygoteProcess` 封裝與三條 Zygote 孵化路徑（`forkSimpleApps` / USAP / `forkAndSpecialize`）**：原書 2.3 將單一 `sZygoteSocket` 與組參數邏輯寫死在 `Process.java` 靜態方法裡；Android 17 抽離為 `ZygoteProcess`（`Process.ZYGOTE_PROCESS` 單例），支援依目標 ABI 在主／副 Zygote（`zygote` / `zygote_secondary`）間動態匹配。Zygote 服務端從 `ZygoteInit.runSelectLoopMode()` 改為 `ZygoteServer.runSelectLoop()` + `ZygoteConnection.processCommand(this, multipleForksOK)`，依情境分化為三條孵化路徑：
>    - **常規快速路徑（`Zygote.forkSimpleApps` → `nativeForkRepeatedly`）**：無 `--invoke-with`、非子 Zygote、未啟用 USAP 且 `peer.getUid() == SYSTEM_UID` 時，直接在 C++ 迴圈內連續 `zygote::forkApp()` 並回寫 5 位元組（big-endian `pid` + `usingWrapper=0`），子進程返回 Java 進入 `Zygote.childMain(argBuffer, null, null)` 再執行 `specializeAppProcess()`。
>    - **USAP 預孵化池路徑（`attemptUsapSendArgsAndGetResult` → `Zygote.childMain`）**：啟用 USAP 且命中 `ZYGOTE_POLICY_FLAG_LATENCY_SENSITIVE`（非系統進程且無 `INVALID_USAP_FLAGS`）時，直接連線 `/dev/socket/usap_pool_primary`，由預先 `forkUsap()` 待機的 `usap64` 進程直接 `accept()`、回傳 `pid`、寫 `writePipe` 通知 `ZygoteServer` 補池，隨即 `specializeAppProcess()`。
>    - **回退／特殊路徑（`Zygote.forkAndSpecialize`）**：用於 `--invoke-with`（`WrapperInit.execApplication`）、`--start-child-zygote`（`ZygoteInit.childZygoteInit`）、非 `SYSTEM_UID` 或 `multipleForksOK == false`，維持單次 JNI 完成 `ForkCommon` + `SpecializeCommon` 並經 `handleChildProc()` / `handleParentProc()` 處理。
> 3. **Binder 執行緒池啟動入口搬家與「延遲開啟 `/dev/binder`」安全邊界**：原書 2.3 的 `RuntimeInit.zygoteInitNative()` 搬移並改名為 `ZygoteInit.nativeZygoteInit()`（JNI `com_android_internal_os_ZygoteInit_nativeZygoteInit` 位於 `AndroidRuntime.cpp`），沿 `gCurRuntime->onZygoteInit()` → `AppRuntime::onZygoteInit()` → `ProcessState::self()->startThreadPool()` → `spawnPooledThread(true)` 建立 `PoolThread` 進入 `IPCThreadState::self()->joinThreadPool(true)`。現代實作移除了 `supportsProcesses()` 檢查，並配合第 5 章的 `ProcessState` 單例設計：Zygote 本身全程不開啟 `/dev/binder`，直到子進程特化完成後才在 `onZygoteInit()` 首次開啟並 `mmap` 專屬 Binder 緩衝區；而子 Zygote（`AppZygote` / `WebViewZygote`）則走 `ZygoteInit.childZygoteInit()` 刻意跳過 `nativeZygoteInit()`，以維持可安全 `fork()` 的單執行緒狀態。
> 4. **清棧跳板由例外改為 `Runnable`、`ActivityThread.main` 整合 `startSeq` 與 DeliQueue 切換**：原書 2.3 的 `RuntimeInit.invokeStaticMain()` 改為 `RuntimeInit.applicationInit()`（設定 `nativeSetExitWithoutCleanup(true)`、`VMRuntime` 目標 SDK／相容性變更、`AppCompatCallbacks.install`）→ `RuntimeInit.findStaticMain()`，不再拋出 `ZygoteInit.MethodAndArgsCaller` 例外，而是返回僅實作 `Runnable` 的 `RuntimeInit.MethodAndArgsCaller` 回到 `ZygoteInit.main()` 執行 `caller.run()`。進入 `ActivityThread.main(String[] args)` 後，除了 `Environment.initForCurrentUser()`、`initializeMainlineModules()` 等每進程初始化外，先解析 `seq=<startSeq>` 與 `--use-deliqueue=<bool>`（在 `Looper.prepareMainLooper()` 之前呼叫 `MessageQueue.setUseDeliQueue(useDeliQueue)`，決定是否啟用 Android 17 無鎖 DeliQueue），接著依序執行 `Looper.prepareMainLooper()` → `new ActivityThread()` → `thread.attach(false, startSeq)`（向 AMS 註冊 `IApplicationThread` 與 `startSeq`）→ `Looper.loop()`。

## 三、各節情景與呼叫鏈（起點 → 終點）

### 12.1 應用程式進程的建立過程（`12.1-create-app-process.md`）
- **情景**：當系統需要啟動一個尚未執行中的應用程式組件（例如第 7–10 章中的 Activity、Service、Broadcast Receiver 或 Content Provider）時，`ActivityManagerService` 透過 `ProcessList` 非同步向 Zygote 請求建立新應用程式進程，並指定入口類為 `android.app.ActivityThread`，最終將新進程推進至 `ZygoteInit.zygoteInit()`。
- **起點 → 終點**：
  - `system_server` 啟動準備與非同步投遞：`ActivityManagerService.startProcessLocked()` → `ProcessList.startProcessLocked(ProcessRecord app, ...)`（計算 `uid`/`gids`/`mountExternal`/`runtimeFlags`/`seInfo`，指定 `entryPoint = "android.app.ActivityThread"`）→ `ProcessList.startProcessLocked(HostingRecord, ...)`（分配 `startSeq = ++mProcStartSeqCounter`、登記 `mPendingStarts`、當 `FLAG_PROCESS_START_ASYNC` 啟用時投遞至 `mService.mProcStartHandler`）→ `ProcessList.handleProcessStart()`（若存在未退出的 `predecessor.getDyingPid() > 0`，先透過 `handleProcessStartWithPredecessor()` 等待前任死亡）→ `ProcessList.startProcess()`（處理 `pkgDataInfoMap`/`bindMountAppsData`/`useDeliQueue`，分流一般 Zygote / `WebViewZygote` / `AppZygote`）
  - Zygote Socket 參數編碼與傳輸：`Process.start()`（選擇 `ZYGOTE_PROCESS` 或 `NATIVE_ZYGOTE_PROCESS`）→ `ZygoteProcess.start()`（定時同步 USAP 池開關）→ `ZygoteProcess.startViaZygote()`（組裝 `--runtime-args`、`--setuid=`、`--setgid=`、`--runtime-flags=`、`--mount-external-*`、`--target-sdk-version=`、`--setgroups=`、`--nice-name=`、`--seinfo=`、`android.app.ActivityThread`、`seq=<startSeq>`、`--use-deliqueue=<bool>`）→ `openZygoteSocketIfNeeded(abi)`（依 ABI 選擇 `primaryZygoteState` 或 `secondaryZygoteState`，連線 `/dev/socket/zygote` 並 `--query-abi-list`）→ `zygoteSendArgsAndGetResult()`（編碼為 `argc + "\n" + args`；依 `shouldAttemptUsapLaunch()` 分流至 `attemptUsapSendArgsAndGetResult()` 或 `attemptZygoteSendArgsAndGetResult()`，等待讀回 `pid` 與 `usingWrapper`）
  - Zygote 服務端接收、三路徑孵化與特化：
    - `ZygoteServer.runSelectLoop()`（`Os.poll()` 監聽 `mZygoteSocket` 與已連線 peer，呼叫 `connection.processCommand(this, multipleForksOK)`）
    - **常規快速路徑**：`ZygoteConnection.processCommand()` → `ZygoteHooks.preFork()` → `Zygote.forkSimpleApps()` → `ZygoteCommandBuffer.forkRepeatedly()` → `nativeForkRepeatedly()`（C++ 迴圈呼叫 `zygote::forkApp()` → `ForkCommon()`；父進程回寫 5 位元組 `pid + 0` 並繼續 `poll()` 下一條簡單命令；子進程返回 `JNI_TRUE`）→ `Zygote.childMain(argBuffer, null, null)` → `Zygote.specializeAppProcess()` → `nativeSpecializeAppProcess()` → `SpecializeCommon()` → `Zygote.setAppProcessName()` → `ZygoteInit.zygoteInit()`
    - **USAP 池路徑（對照）**：`ZygoteServer.fillUsapPool()` 預先 `Zygote.forkUsap()` → `nativeForkApp()` → 子進程進 `Zygote.childMain(null, usapPoolSocket, writeFD)` 改名 `usap64` 並 `accept()`；收到 `ZygoteProcess` 連線後直接回傳 `pid`、寫 `writePipe` 通知 `ZygoteServer` 補池，隨即 `specializeAppProcess()` → `ZygoteInit.zygoteInit()`
    - **回退／特殊路徑（對照）**：`ZygoteConnection.processCommand()` → `Zygote.forkAndSpecialize()` → `nativeForkAndSpecialize()`（單次完成 `ForkCommon` + `SpecializeCommon`）→ 父進程 `handleParentProc()` 回寫 `pid` 與 `usingWrapper`；子進程 `handleChildProc()` 分流 `WrapperInit.execApplication()` / `ZygoteInit.childZygoteInit()` / `ZygoteInit.zygoteInit()`
  - `system_server` 回填啟動狀態：`ProcessList.handleProcessStartedLocked()`（自 `mPendingStarts` 移除、寫入 `app.setPid(pid)` 與 `mService.addPidLocked(app)`、若尚未 `procAttached` 則排程 `PROC_START_TIMEOUT_MSG`）。

### 12.2 Binder 執行緒池的啟動過程（`12.2-start-binder-thread-pool.md`）
- **情景**：新應用程式進程經 `ZygoteInit.zygoteInit()` 完成標準輸出重新導向與執行期通用初始化後，立即在原生層首次開啟 `/dev/binder` 並啟動 Binder 執行緒池，使後續 `ActivityThread.attach()` 得以透過 Binder 向 AMS 註冊 `IApplicationThread` 並接收系統服務回呼。
- **起點 → 終點**：
  - Java 入口與執行期通用初始化：`ZygoteInit.zygoteInit()` → `RuntimeInit.redirectLogStreams()` → `RuntimeInit.commonInit()` → `ZygoteInit.nativeZygoteInit()`
  - 跨層回呼 `AppRuntime`：`AndroidRuntime.cpp::com_android_internal_os_ZygoteInit_nativeZygoteInit()` → `gCurRuntime->onZygoteInit()`（`gCurRuntime` 由 Zygote 啟動期建立並經 `fork()` CoW 繼承至所有應用程式進程）→ `app_main.cpp::AppRuntime::onZygoteInit()`
  - 開啟驅動與建立執行緒池：`ProcessState::self()`（`ProcessState::init("/dev/binder", false)`：子進程首次開啟驅動並 `mmap` 專屬 Binder 緩衝區，避免與 Zygote 共享 fd）→ `ProcessState::startThreadPool()`（`std::unique_lock<std::mutex>` 檢查 `mThreadPoolStarted`）→ `ProcessState::spawnPooledThread(true)`（命名 `binder:<pid>_<seq>`、`sp<PoolThread>::make(true)`、`t->run()`、`mKernelStartedThreads++`）→ `PoolThread::threadLoop()` → `IPCThreadState::self()->joinThreadPool(true)`（對照 `ZygoteInit.childZygoteInit()` 為何刻意跳過 `nativeZygoteInit()`）。

### 12.3 消息循環的建立過程（`12.3-create-message-loop.md`）
- **情景**：新應用程式進程啟動 Binder 執行緒池後，透過 `MethodAndArgsCaller` 跳板清除 Zygote 孵化階段的呼叫堆疊，進入 `ActivityThread.main()` 完成主執行緒 `MessageQueue`（含 DeliQueue 旗標切換）與 `Looper` 的初始化、攜帶 `startSeq` 向 AMS 報到，並進入 `Looper.loop()` 等待系統與應用程式消息。
- **起點 → 終點**：
  - 反射查找與 `Runnable` 清棧跳板：`ZygoteInit.zygoteInit()` → `RuntimeInit.applicationInit()`（`nativeSetExitWithoutCleanup(true)`、`VMRuntime` 設定 `targetSdkVersion` / `disabledCompatChanges`、`AppCompatCallbacks.install()`、解析 `RuntimeInit.Arguments` 取得 `startClass = "android.app.ActivityThread"` 與 `startArgs = ["seq=<startSeq>", "--use-deliqueue=<bool>"]`）→ `RuntimeInit.findStaticMain()`（`Class.forName` 載入並檢驗 `public static void main(String[])`，返回 `new RuntimeInit.MethodAndArgsCaller(m, argv)`）
  - 退回頂層呼叫堆疊並啟動入口：`MethodAndArgsCaller` 沿 `handleChildProc` / `childMain` → `processCommand` → `ZygoteServer.runSelectLoop()` 一路返回 `ZygoteInit.main()` → `finally` 關閉 Server Socket → `caller.run()` → `MethodAndArgsCaller.run()` 透過 `mMethod.invoke(null, new Object[] { mArgs })` 呼叫 `ActivityThread.main(args)`
  - `ActivityThread.main()` 初始化與進入消息循環：
    - 每進程環境初始化：`AndroidForwardingOs.install()`、`CloseGuard.setEnabled(false)`、`Environment.initForCurrentUser()`、`TrustedCertificateStore.setDefaultUserDirectory()`、`initializeMainlineModules()`、`Process.setArgV0("<pre-initialized>")`
    - 參數解析與 `MessageQueue` 實作選擇：掃描 `args` 提取 `seq=<startSeq>`，並依 `--use-deliqueue=<bool>` 在建立 `Looper` 之前呼叫 `MessageQueue.setUseDeliQueue(useDeliQueue)`（決定底層使用 `LegacyMessageQueue` 或無鎖 `CombinedDeliMessageQueue`）
    - 主迴圈建立與向 AMS 報到：`Looper.prepareMainLooper()`（呼叫 `prepare(false)` 綁定不可退出的主執行緒 `Looper` 並設為 `sMainLooper`）→ `new ActivityThread()` → `thread.attach(false, startSeq)`（`RuntimeInit.setApplicationObject(mAppThread.asBinder())`、`ActivityManager.getService().attachApplication(mAppThread, startSeq)` → 對照 `AMS.attachApplicationLocked()` 如何以 `startSeq` 認領非同步啟動的 `ProcessRecord`；另註冊 `BinderInternal.addGcWatcher` 與 `ViewRootImpl.addConfigCallback`）→ `sMainThreadHandler = thread.getHandler()` → `Looper.loop()` 永駐消息迴圈（第 13 章接續解剖 `MessageQueue` / `Looper` / `Handler` 內部實作）。

|---|---|---|---|
| `ActivityManagerService.startProcessLocked()`（持全域鎖同步呼叫 `Process.start()`） | `AMS.startProcessLocked()` 轉發 `ProcessList.startProcessLocked()` → `mProcStartHandler`（`ProcStartHandler`）非同步執行 `handleProcessStart()` → `startProcess()` → `handleProcessStartedLocked()` | 搬家 + 架構重構 | 移出 AMS 鎖外非同步孵化，降低系統鎖競爭；加入 `startSeq` / `mPendingStarts` 處理搶先 attach 競態、前任死亡等待 `predecessor.getDyingPid()`、資料目錄隔離與 `WebViewZygote`/`AppZygote` 分流 |
| `Process.start()`（含 `supportsProcesses()` 單進程模擬分支） | `Process.start()`（依 `ZYGOTE_POLICY_FLAG_NATIVE_PROCESS` 分派至 `ZYGOTE_PROCESS` 或 `NATIVE_ZYGOTE_PROCESS`） | 邏輯改變 | 移除單進程執行緒模擬分支；回傳值由 `int pid` 改為 `ProcessStartResult(pid, usingWrapper)`；新增 `startWebView()` 等介面 |
| `Process.startViaZygote()` / `zygoteSendArgsAndGetPid()` / `openZygoteSocketIfNeeded()`（單一靜態 `sZygoteSocket`） | `android.os.ZygoteProcess`（`start()`、`startViaZygote()`、`openZygoteSocketIfNeeded(abi)`、`zygoteSendArgsAndGetResult()`、`attemptZygoteSendArgsAndGetResult()`、`attemptUsapSendArgsAndGetResult()`） | 抽離搬家 + 邏輯擴充 | 封裝為 `ZygoteProcess` 物件；支援主／副 Zygote 依 ABI 匹配與 `--query-abi-list`；新增 USAP 預孵化池直連路徑與大量安全／隔離／相容性／DeliQueue 參數 |
| `ZygoteInit.runSelectLoopMode()`（`selectReadable`） | `ZygoteServer.runSelectLoop()`（`Os.poll(StructPollfd[])`） | 抽離搬家 + 邏輯改變 | 伺服器輪詢搬至 `ZygoteServer`，改用 `Os.poll` 並整合 USAP 事件 fd 與回報 pipe 管理 |
| `ZygoteConnection.runOnce()` → 固定 `Zygote.forkAndSpecialize()` → `handleChildProc()` | `ZygoteConnection.processCommand(zygoteServer, multipleOK)`：預設走 `Zygote.forkSimpleApps()`（`ZygoteCommandBuffer.nativeForkRepeatedly` + `Zygote.childMain` + `specializeAppProcess`）；另支援 USAP 池路徑與回退 `Zygote.forkAndSpecialize()` | 改名 + 邏輯大幅擴充 | 預設由 C++ 迴圈批量處理簡單 fork 請求並拆分 fork 與 specialize 兩階段；`--invoke-with` / `--start-child-zygote` 才回退 Java `forkAndSpecialize()`；回傳 `Runnable` 而非 `boolean` |
| `RuntimeInit.zygoteInit()` + `RuntimeInit.zygoteInitNative()`（JNI `com_android_internal_os_RuntimeInit_zygoteInit`） | `ZygoteInit.zygoteInit()` + `ZygoteInit.nativeZygoteInit()`（JNI `com_android_internal_os_ZygoteInit_nativeZygoteInit`，仍於 `AndroidRuntime.cpp`）；另有 `ZygoteInit.childZygoteInit()` | 搬家 + 改名 | Zygote 子進程初始化入口統一歸入 `ZygoteInit`；子 Zygote 透過 `childZygoteInit()` 刻意跳過 Binder 執行緒池啟動 |
| `AppRuntime::onZygoteInit()`（檢查 `proc->supportsProcesses()` 後呼叫 `proc->startThreadPool()`） | `AppRuntime::onZygoteInit()` 直接呼叫 `ProcessState::self()->startThreadPool()`；`ProcessState.cpp` 搬至 `platform/frameworks/native/libs/binder/` | 搬家 + 邏輯簡化 | 移除 `supportsProcesses()` 檢查；`ProcessState` 改用 `std::mutex`、`sp<PoolThread>::make(isMain)`、`mKernelStartedThreads++` 與 `binder:<pid>_<seq>` 命名 |
| `RuntimeInit.invokeStaticMain()` **拋出** `ZygoteInit.MethodAndArgsCaller extends Exception`，由 `ZygoteInit.main()` `catch` 執行 | `RuntimeInit.applicationInit()` → `RuntimeInit.findStaticMain()` **返回** `RuntimeInit.MethodAndArgsCaller implements Runnable`，由 `ZygoteInit.main()` 執行 `caller.run()` | 搬家 + 邏輯改變 | 清棧跳板由拋出例外改為返回 `Runnable`，消除例外建構與展開成本；新增 `nativeSetExitWithoutCleanup(true)`、`VMRuntime` 與 `AppCompatCallbacks.install()` |
| `ActivityThread.main(String[] args)`（直接 `Looper.prepareMainLooper()` → `thread.attach(false)` → `Looper.loop()`） | `ActivityThread.main(String[] args)`（新增 `AndroidForwardingOs.install()`、`Environment.initForCurrentUser()`、`initializeMainlineModules()`、解析 `seq=` 與 `--use-deliqueue=` 呼叫 `MessageQueue.setUseDeliQueue()` → `Looper.prepareMainLooper()` → `thread.attach(false, startSeq)` → `Looper.loop()`） | 邏輯擴充 | 透過 `startSeq` 閉合非同步啟動競態；支援在建立主執行緒 `MessageQueue` 前動態切換傳統 `LegacyMessageQueue` 或無鎖 `CombinedDeliMessageQueue` |
